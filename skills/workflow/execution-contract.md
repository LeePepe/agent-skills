# CLI 与 subagent 执行规范

适用于与 CLI 进行开发需求沟通、规划、直接实现、委派 subagent，以及显式启动 Dev Team。
CLI 入口和角色引用本文件，不各自维护一份流程。目标仓 `AGENTS.md`、固定合同、权限和 required gates 继续有效；
仓库更严格的计划／审查要求优先。本规范不授予发布、受保护操作或在途版本变更权限。

## 准入与粒度

- 事实问答、调查和方案讨论先产出判断，不因读取本规范自动实施、派团队或启动 subagent。
  明确且范围清楚的实施请求已经表达执行意图，不重复索取相同授权。
- 小改动可在既有 issue、会话记录或仓库文档中写一个 target、一个 task；不为流程新建规划目录、任务系统或主管角色。
  仓库明确允许免计划的变更沿用该例外。选择直接 CLI 执行不强制转成 Dev Team。

| 单元 | 职责 | 完成条件 |
|---|---|---|
| Goal | 可观察的最终结果、范围及整体验收 | 必需 target 全部交付，端到端验收有证据 |
| Target | 一个可独立验收的交付结果，通常一个 PR，保持唯一实现责任人 | 所含 task 经独立验收、仓库交付门禁满足；明确区分本次实现输出与最终交付 |
| Task | target 内的实现／验证步骤 | 输出与验证证据齐全；执行者完成标记仍待 target 独立确认 |

按结果、真实接口和依赖拆 target，允许跨层；必须原子成立的生产者与消费者改动放在一起。
跨仓发布、消费者升级和真实消费分别取证。Task 不自动变成 issue、PR、agent 或审查轮次。

## Plan 与执行基线

需要计划的实现先形成可审内容：Goal 验收项、target 划分／责任／依赖、task 到验收项的映射、接口与权限边界、
验证办法，以及必要的中途检查点。按目标仓规定一起接受独立计划审查和执行确认，不能先实施再补审。
不要把总体 plan、target 拆分、task 拆分分别重复审批。

影响方案成立的 SDK 能力、并发保证、真实测试入口等先做最小可行性验证；允许的只读调查或隔离验证不等于生产实施。
整体 target／依赖先明确，近期 task 写细；后续内部展开不得偷偷改变已批准契约。

区分两类内容，保持一份权威来源：

- **受审基线**：结果／范围、行为与兼容性、接口／架构、验收、权限、交付依赖和必要审查检查点。
  变更这些内容时固定新 revision，由独立 reviewer 检查变更及影响面；需要 Owner 新决定时沿原入口处理。
- **执行台账**：进度、PR／head、验证证据、交接／等待状态，以及不改变上述基线的内部步骤补拆。
  更新台账不改变受审基线，也不触发新设计审批；正常缺陷与必要测试留在原 target、原执行者处理。

台账默认与受审 artifact 分开，引用其准确 revision。若目标仓要求审查的 artifact 本身被修改，仍须刷新该准确版本的审查证据；
可限定变更及影响面，不把它变成全方案重新讨论或重新索取未变的执行授权。旧 verdict 不声称覆盖未审的新内容。

## 执行与委派

同一个 target 由原执行者按依赖逐步实现、验证、修复，保留已有上下文；共享文件／接口保持唯一写者。
只读探索、日志分析及接口／路径不冲突的工作可并行。正常 task 完成无需逐次交编排者回执或换 agent。

委派时显式携带本规范路径、目标仓规范入口、受审基线及授权来源、target／task 与验收项、owned paths、唯一执行者、
验证／审查责任和预期回报。不要假设 subagent 自动继承个人 skill 或读取更新。实现者负责构建、测试和自检；
编排者管理依赖与异常，不再创建一层 supervisor。执行结果未知先对账，不重派第二写者。

## 独立验收与复审

正式实现审查默认在 target 候选完成后进行。独立 reviewer 直接读基线、完整候选 diff 和证据，逐项确认 task／验收项，
不把执行者勾选或报告当事实。记录：验收项／task、实现位置、验证证据、结论（已确认／缺失／待人工验证）。
缺失必要证据不能算已通过；reviewer 独立于实现者，不能自行签收自己的实现。

复用目标仓已要求且覆盖相同职责的独立审查；只补覆盖缺口，不增加重复的全量审查链或 reviewer 报告审查。
Dev Team 保留 pre-push spec／architecture 与 PR head defects／standards 的现有分工；自动 checks 由执行者／CI 运行，
内容 reviewer 不重复运行或裁定它们。只在后续高度依赖、返工代价大的契约或安全边界安排必要中途检查，并写进 plan。

- 首轮覆盖完整 target 和全部验收项，列全有证据的阻塞，不每轮另选一个检查重点。
- 后续沿用 findings：逐项确认修复，检查 repair diff 及影响面，保留完整 target 的覆盖记录。
  新发现的既有漏项明确标记及说明；真实阻塞不因发现较晚而隐藏，改进建议不冒充新需求。
- 新 implementation SHA 按仓库要求刷新准确 head 的 review／CI 证据。复审范围可以限定，旧 SHA 的 PASS 不能充当新 SHA 的证据。
- 同一根问题两轮修复／验证／复查无实质进展，由团队 TL 或原主会话诊断设计、实现、测试、环境或要求冲突，给出具体下一动作。
  遵守既有轮数／最终轮限制，不靠改名、换 run／SHA／agent 重置历史；仍无解或需产品／权限／政策决定时沿原升级入口。

## 台账与收口

复用现有 plan／issue 的执行记录，每 target 一行：责任人、状态、当前 PR／head、未解决 findings、证据链接、下一动作或 HOLD。
从 Git／PR 读取当前 head，交接引用该来源，不在评论、manifest 和 plan 中人工维护多套状态。
review／CI 仍固定实际 revision；台账只是索引，不能覆盖真实证据。

执行者回报 task 输出和限制，独立 reviewer 确认落实，交付方证明合并与门禁，原编排者逐项核对 Goal 的整体验收。
需要发布／实机／真实消费者的验收保留待完成状态，不能由 task 勾选、CI 绿或 PR merged 推断完成。
如已有时间戳和执行记录，可观察交付耗时、等待占比、同根返工和审查漏项；不为统计另建一套汇报流程。
